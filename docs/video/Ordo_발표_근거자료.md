## 1. 무엇을 요구받았는가

### 1-1. 출발점 (1차 기획 SLAFlow)
- 독립 ITSM: AI 트리아지 + SLA 타이머 + 승인 워크플로우 + 대시보드 + 월간 보고서
- 외부 AI(Gemini), AWS 배포 계획
- 위험 점수표(+3·+3·+3·+2·+2·+1, Low~Critical) — **현재도 숫자 그대로 사용**

### 1-2. 시스원 이사님 피드백 9개 → 반영 상태

| 피드백 | 반영 | 상태 |
|---|---|---|
| 기존 시스원 ITSM(백오피스) 활용 | 독립 시스템 → 백오피스 앞단 어시스턴트 | 🟢 방향 전환 · 🟡 실제 백오피스 연결은 목업 |
| MSP 본부 내부 소통 | 역할 5개 (요청자·고객사 관리자·운영 담당자·승인자·운영 관리자) | 🟢 |
| 자연어로 쉬운 등록·사용 | 대화 → 초안 → 사람 확인 후 접수 | 🟢 |
| 백오피스 이벤트 실시간 | 장애 발생 · SLA 임박 알림 (SSE) | 🟢 알림 · 🟡 이벤트 원천(AiWACS)은 시연 API |
| 접속 없이 조회 | 대화형 조회 도구 | 🟢 |
| AI 에이전트 | LLM Function Calling, 역할별 도구 | 🟢 |
| **로컬 LLM 필수** | Gemini 제거 → 교육원 DGX Spark · Ollama · qwen2.5:7b | 🟢 (Gemini 엔진 코드는 남아 있으나 설정상 비활성) |
| 연결 지점 정의 | 접수 · 조회 · 이벤트 3곳 | 🟢 정의 · 🟡 실연동 없음 |
| 목업 | 대화·요청서 화면 + 백오피스 목업 화면 | 🟢 |

### 1-3. 확인하지 못한 가정 (2차 미팅 취소)
- 내부 고객 = MSP 본부에 요청하는 사용자
- 백오피스 = 시스원 공개 ITSM 구성(서비스데스크·장애/변경·SLA·모니터링 이벤트) 기준 목업

## 2. 어떻게 설계·구현했는가

### 2-1. 핵심 원칙: AI는 추출 · 규칙은 판정 · 사람은 결정 🟢

| 단계 | 담당 | 코드 |
|---|---|---|
| 추출 | 로컬 LLM — 유형·분류·시각·위험 요인 + 원문 근거, 도구 선택 | 📁 `triage/engine/OpenAiCompatibleTriageEngine.java`, `assistant/AssistantService.java` |
| 판정 | 서버 규칙 — AI 결과 교정·보완, 점수 계산 | 📁 `triage/TriageValidator.java`, `risk/RiskPolicy.java` |
| 결정 | 사람 — [접수하기] 버튼이 API 직접 호출 | 📁 `POST /api/tickets/{id}/submit` (AI 도구 아님) |

- AI에게 **승인·상태 변경·취소 도구 없음** 🟢 (도구 4개뿐, 3장 참고)
- 승인·상태 변경 **API 자체도 없음** 🟢 — `approvals`, `ticket_comments` 테이블은 설계만 있고 미사용

## 3. API 및 AI 도구 명세 (실제 코드 기준) 🟢

> ⚠️ `docs/api.md`는 9월 설계 단계 문서라 실제와 다름 (승인 API 등 미구현 항목 포함, **예시에 시연 비밀번호 노출**). 아래 표가 실제 구현

### 3-1. REST API (14개)
권한 검사는 컨트롤러·서비스 코드에서 직접 수행 (`@PreAuthorize` 미사용)

| 메서드 | 경로 | 누가 | 하는 일 |
|---|---|---|---|
| POST | `/api/auth/login` | 누구나 | 로그인 → JWT. 실패 사유 구분 없이 동일 오류 |
| GET | `/api/auth/me` | 로그인 사용자 | 내 정보 |
| POST | `/api/assistant/chat` | 로그인 사용자 (역할별 도구) | 대화 한 턴. 메시지 5000자, 이력 20개 |
| POST | `/api/tickets` | 고객사 측만 | 바로 접수(대화 거치지 않는 경로) |
| GET | `/api/tickets` | 테넌트 범위 | 목록 (최신순, 남의 초안 제외) |
| GET | `/api/tickets/{id}` | 테넌트 범위, 위반 시 403 + 감사 | 상세 (장애면 1차 통보 기한 포함) |
| POST | `/api/tickets/{id}/submit` | **요청자 본인, 초안만** | 접수 → SLA 시작 |
| POST | `/api/tickets/{id}/supplement` | 요청자 본인, 초안·보완 대기만 | 확인 질문 답변 → 재분석·재평가 |
| POST | `/api/tickets/{id}/triage` | 테넌트 범위 | AI 분석 재실행 |

### 3-2. AI 도구 (4개)
📁 `assistant/AssistantToolRegistry.java`, `AssistantToolDispatcher.java`

| 도구 | 입력 | 역할 | 하는 일 |
|---|---|---|---|
| `create_request` | `text` (요청 원문) | 요청자 · 고객사 관리자 | **초안**(DRAFT) 생성 + 분석. SLA 시작 안 함 |
| `list_my_requests` | `status` (선택) | 요청자 · 고객사 관리자 | 최신 10건 (요청자는 본인 것, 고객사 관리자는 고객사 전체) |
| `list_requests` | `status` (선택) | 운영 담당자 · 승인자 · 운영 관리자 | 테넌트 범위 최신 10건, 남의 초안 제외 |
| `get_request` | `ticketNo` | 전 역할 | 상세 + 최신 분석, 테넌트 범위 |

- 한 턴에 모델 호출 최대 **3회**, 대화 이력 **20개**
- 클라이언트가 보낸 `tool` 역할 메시지는 버림 (조작 방지)
- 실행 직전 역할 재검사 → 허용 안 된 도구면 `ACCESS_DENIED` 감사
- 모든 도구 실행 `ASSISTANT_TOOL_CALLED` 감사
- **텍스트 도구 호출 복구** 📁 `ToolCallRecovery.java` — 모델이 도구를 글자로 쓰면 3가지 형식(`<tool_call>` 태그 · JSON · `함수명(...)`) 파싱, **역할 허용 도구만** 실행, 화면에서는 제거
- 2차 응답이 비면 1회 재시도 → 그래도 비면 결과 카드로 템플릿 답변
- 최종 답변의 영어 코드 → 한글 치환

**판단 기준 (시스템 프롬프트 요약)**
1. 질문 신호("어떻게", "뭐가 필요", "?") + 구체 대상·시각·본인 행동 없음 → 설명만
2. 지난 요청 질문 → 목록 도구
3. 요청 번호 언급 → 상세 도구
4. 구체적인 작업·장애 → `create_request` (대상·시각·본인 행동·장애 증상 중 2개 이상)
